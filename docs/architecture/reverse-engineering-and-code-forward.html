Fixed-Income RFQ Trading Platform — Reverse-Engineering & Code-Forward Architecture

Repository COG-GTM/Fixed-Income-RFQ-Trading-Platform · commit 0b72d81 · Sections 2–5 are observed from source; sections 6–7 are proposed. Paths are relative to monolith/src/main/java/com/javieraviles/splitthemonolith/ unless stated.

1. Goals

This document is a knowledge base of the platform as implemented and a proposal for a domain-driven re-architecture with an incremental (strangler) roadmap. It is not a platform, runtime or language upgrade, and no application code was changed to produce it. The focus requested was data ownership between the monolith and any extracted services, plus pricing/market-data and messaging integrations.

2. System as-is observed

One deployable: a Spring Boot 2.2.6 / Java 11 REST service on port 8080 with an H2 in-memory database (monolith/pom.xml:9-19, application.properties:2). There is no UI, no scheduler and no message broker. The only external dependency is an optional trade-confirmation service at http://localhost:8070/, reached through a feature toggle that is off by default (application.properties:3-4). The extracted orders and notifications services referenced by the project's history were deleted in commit 78706eb; only the HTTP client and toggle remain in the monolith.

6. Re-architecture proposed

Six contexts fall out of the ownership table: one per table with a single natural owner, one anti-corruption layer per external system (including the pricing seam that does not exist yet), and a read model for the blotter.

Design rules

  1. One writer per table. Other contexts change state only by command and observe it only by event.
  2. Entities never leave their context; each context publishes a DTO contract validated with @Valid.
  3. Side drives direction: BUY reserves inventory and credit; SELL releases inventory and settles cash.
  4. Money = amount + currency + declared scale and rounding rule. Dates = trade, settlement and business date; maturity is checked at quote time.
  5. External calls happen after commit through an outbox; delivery failures are events, not HTTP 500s.
  6. Seed data is a profile-scoped fixture, not a startup job.
